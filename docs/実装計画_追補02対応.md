## 全体方針

追補02は **データモデルの根本刷新 (R1: 担当統合) + 新規機能群 (R10/R11/R13-16) + 印字系リプレース (R6/R7)** が混在する大きな改修。

以下の原則で進める:

1. **データモデル先行**: R1 (担当・本指名の統合) が他の多数の要件の前提。**まず型を確定**させる。
2. **小さな PR を連鎖**: 一度に全要件は入れない。1 PR = 1 主題で 9 本に分割。
3. **計算ロジック・印字出力は最後**: UI と疎結合な計算系 (`utils/`) は PR 後半で確実に切り替える。
4. **既存データ互換を守る**: `Cast`/`Table` は optional フィールド追加で移行する。モックデータは段階的に更新。
5. **PR は push 後に全部のコミットが揃っていることを確認してからマージ依頼**する (過去 3 回取り込み漏れを起こしたため)。

## バックエンド準備との関係

**方針**: 本追補 02 対応は **フロントの mock ベースで全完了させる** 。バックエンド移行は、データ構造が安定した後 (= PR A〜H マージ後) に着手する。

理由:
- 追補 02 で型が大きく変わる (Table の担当構造、StoreSettings、ReceiptNumber 等)
- モックで UI を完成させてから Firestore 設計に落とし込む方が、スキーマ迷走が減る
- 先方は現時点でモックを見ているため、**ユーザー体験の完成度を優先**する

バックエンド移行時の叩き台は以下 (後日別計画書で詳述):
- Firestore: `stores/{storeId}/{tables,casts,billingRecords,attendance}`
- Firebase Auth: email/password (店舗ごとにアカウント管理)
- Cloud Functions: 領収書番号発番、バック計算などのサーバー側整合
