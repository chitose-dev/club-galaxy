## 3. データモデル変更案（比較）

ギャップ G1 を解決するための 3 案。**推奨は案 A**。

### 案 A: メニュー側 (`CastMenuItem`) の `price` を単価としてそのまま使い、集計キーを `BackType` × `price` の複合にする
- 変更点
  - `DailyWork.backs` を `Partial<Record<BackType, number>>` から
    `Partial<Record<BackType, Partial<Record<number /* unitPrice */, number /* count */>>>>` に拡張
  - `receiptSnapshot.orders[].menuItem` に `backType: BackType` と `price: number` が必須であることを型で明示し、保存パスでの欠落を防ぐ
  - `Cast.backRates` は現行通り `BackType` 単位のレート（円 / 本）を保持。**「メニュー単価」と「キャストバック単価」は別概念**であることを明示する設計。
- メリ
  - 既存スキーマからの差分が小さい。`BackType` 列挙はそのまま、追加情報は数値だけ
  - 単価は「メニューの価格スナップショット」なので新規入力フィールドは増えず、既存運用（メニュー価格を管理画面から編集）と整合
  - 過去レコードも `receiptSnapshot.orders[].menuItem.price` から後付け再集計が可能（マイグレーション不要）
- デメ
  - `backs` がネスト構造になり、フロント側の代入・走査ロジックを書き換える必要がある
  - 単価が変動した日をまたぐ集計で、表示単価を「最頻値 / 月初値 / 月別小計」のどれにするか決める必要（→ §3.4）

### 案 B: `BackType` 列挙を単価込みに細分化する（例: `FD150` / `FD200` / `Fカク200` / `Fカク250` 等の新リテラル）
- メリ
  - `backs` の形は `Partial<Record<BackType, number>>` のまま、PDF カラム定義もリテラルで素直に書ける
- デメ
  - **メニュー価格変更（管理画面で日常的に行う想定）と列挙型がカップリング**し、価格改定のたびに型・既存データのマイグレーションが必要
  - 既存 `BackType` 17 種のリテラル比較箇所（`PERCENT_BACK_TYPES`、`Cast.backRates` キー、UI ラベル等）に広範囲に波及
  - 過去 17 種で書かれた Firestore レコード・テストデータの後方互換層が必要

### 案 C: 別コレクション `dailyDrinkCounts` を新設し、(castId, businessDate, backType, unitPrice) を行とする
- メリ
  - 既存 `DailyWork` を一切いじらず、追加情報を別レイヤーで扱える
  - 単価別の柔軟な集計クエリが組める（Firestore index 設計次第）
- デメ
  - DailyWork と同期する第二の集計キャッシュが増え、整合性責任が増す（M14「上書き保存」方針との衝突）
  - フロント側で 2 ソース突き合わせが必要、テスト面の負荷が高い
  - 現状のモック・サンプル・型生成の構造から外れて開発コスト大

### 3.4 案 A 採用時の細部
- **PDF 表示単価の決定**: 月内で単価が変動した場合、`receiptSnapshot.orders[].menuItem.price` の集合をユニーク化してカラム見出しに併記（例: `Fドリンク (150 / 200)`）し、列内では単価別に行内サブセルを描く。手書き運用と同じ視覚構造になる。
- **キャストバック単価との関係**: 「販売単価」と「キャストバック単価」(`Cast.backRates`) は別。`backTotal` の計算式は現行通り `count × backRates[backType]` のまま維持し、PDF の `金額` セルでは「販売単価 × 本数 = 売上寄与額」を表示する（手書き表の右半セルは販売金額であって、キャストへのバック額ではない）。これは仕様確認事項として §6 に記載。

## 4. 日経表 PDF カラム構成案

### 4.1 ヘッダ構成
- 1 段目: `日 / 時間 / 日給 / Fドリンク / 本ドリンク / Fカクテル / 本カクテル / 本カクW / 同伴 / 本指 / 場内 / ボトルバック / その他 / P合計 / 日給合計 / ホステス税 / 総支給額`
- ドリンク系列（Fドリンク・本ドリンク・Fカクテル・本カクテル）の見出しに**単価リスト**を併記:
  - `Fドリンク (150 / 200)`、`本ドリンク (250)`、`Fカクテル (200 / 250)`、`本カクテル (400)`
- 2 段目（ドリンク列のみ）: 各単価セルを `本 / 金額` で 2 サブカラムに分割

### 4.2 セルレンダリング方針
- ドリンク系列セル: 単価ごとに `<本数> / <販売金額>` を 2 サブセル併記。0 本の単価サブセルは空文字（手書きと同じく強調しない）
- バック系列（同伴 / 本指 / 場内 / ボトルバック / その他）: 単価分割しない 1 セル `本(¥金額)` を維持（手書きも 1 セル）
- ホステス税列は全行「`〃`」（繰り返し記号）を表示。既存実装の `-¥<額>` 表記から手書き準拠に変更
- 欠勤日: 日付行ごと空白（日付セルのみ表示し、時間・日給・バック列を空文字）。`hours === 0 && Object.keys(backs).length === 0` で判定

### 4.3 右上 参考情報ボックス
- 既存「先月売上」「当月売上」表示の右に**参考情報枠**を追加
  - **①** `<金額>` （手書きでは黄シール）
  - **②** `<金額>` （手書きでは緑シール）
  - 凡例として「先月売上 ¥<額> ・ <P>p」
- ①② のデータソースは現時点で意味未確定（§6）。スキーマ追加は意味確定後に行う方針とし、**v1 では UI 上に枠だけ用意し、値は空欄 or `--` を入れる**。意味が確定したら算出ロジック / プロパティ追加を別 PR で。

### 4.4 列幅・レイアウト調整
- A4 横、`@page { size: A4 landscape; margin: 10mm; }` 維持
- ドリンク列のサブカラム分割で横幅が逼迫するため、`font-size` を現行 9px から 8.5px へ縮小、`padding: 1px 2px` まで詰める
- `<colgroup>` を導入し、ドリンク系列は固定幅、合計系列はフレキシブル幅で割り当てる

- `DailyWork.backs` 構造変更による既存キャッシュとの非互換に注意。`computeDailyWork` はレシートから都度再集計しているため、既存 Firestore キャッシュは破棄して再生成する運用で吸収可能
